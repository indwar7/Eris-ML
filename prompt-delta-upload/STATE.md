## The task

Given prompt A, prompt B (= A after ONE hidden edit), and a hidden model's
behaviour fingerprint on held-out inputs, recover:
  1. which edit op produced B (known vocabulary, ~12 ops)
  2. which input slice the edit actually MOVED

Submitted artifact = (edit_op, affected_slice) pair — deliberately not a
number and not a single label, to clear rejection rule 2.2
(regression/ranking/classification all auto-reject or cap).

## Prior art — both obvious framings are OCCUPIED, do not use

- "predict how sensitive a prompt is" -> PromptSET / arXiv 2502.06065
  (11,469 prompts x 9 variations). Also a scalar => regression => auto-reject.
- "reconstruct the prompt text from outputs" -> LLM inversion: PTP
  (2607.29378), PROVE (2608.13671), output2prompt, Reverse Prompt Engineering.
- **UNOCCUPIED axis: which input slice an edit moved.** 2502.06065 explicitly
  treats "each prompt pair as an isolated case rather than analyzing which
  input subcomponents drove the sensitivity."
- Rule 2.1: these are CLOSE neighbours -> naming them prominently triggers
  cite-or-cap and DROPS novelty. Cite distant antecedents instead
  (e.g. heterogeneous treatment effects / subgroup identification) and
  differentiate.

**Why the design survives the shortcut:** fmt_json has the HIGHEST regex
recall (1.00) but a LOW slice spread (0.59) — knowing the op tells you almost
nothing about the slice. The two halves are near-independent, so the
regex-free ops stay free on half the answer and pay nothing on the other.
This is why the slice is the graded axis, not the op alone.

## Item definition (LOCKED 2026-09-12)

    item = (family, edit_op, slice_subset)

Not (family, edit_op) — that yields only 132 items, train=105, far below the
platform minimum of 1000 (register rule 4). And not repeated "views" of the
same (family,op): every view would share ONE answer, so the test set would
count the same answer V times.

Instead each item shows a DIFFERENT SUBSET of K=4 of the 6 slices. The
"which slice moved most" answer is therefore genuinely re-decided per item
(the argmax over a different candidate set), and the released fingerprint
differs per item too. This multiplies items without duplicating answers.

    families 12 x edit_ops 11 x C(6,4)=15 subsets = 1,980 items
    generations needed = 12 x 12 ops x 6 slices x 4 probes = 3,456 (~30 min GPU)

**Title changed from register-safe default, user's explicit choice:**
"The Edit That Moved the Answer" (fallback noted above).

**Label rule rewritten after finding a 100%-accuracy shortcut** (rule 2.6):
first version labeled with plain Euclidean distance on the released
per-slice MEAN fingerprint -- an attacker recomputing that exact same
distance on the exact released numbers matched the true label 100% of the
time, because it WAS the label rule. Fixed by computing the label from
per-probe (not per-slice-mean) standardized fingerprints as
mean_shift + 0.5*variance_shift; the per-probe variance is never released,
only the per-slice mean is, so the same "recompute Euclidean on what you
were given" attack now caps at 51.7%, comfortably inside the 0.4-0.7 target
band instead of solving the task outright. See prepare.py's "LABEL RULE"
docstring section for the full derivation.

**Balancing**: raw label distribution was skewed per family (some slices,
e.g. "ambiguous"/"unanswerable", move far more often across ops for this
model) -- a majority-vote-among-candidates baseline hit 0.43 before
balancing. Fixed by capping each family's per-label item count to
ceil(even_share * 1.10), dropping the highest-margin (easiest) items first.
Post-balance majority-baseline: 0.264 (chance floor).

**Test-family selection**: rule 4 requires splitting by family, never by
row. Because balancing changes how many items survive per family, a fixed
shuffle-and-slice no longer reliably lands the test/train ratio in
15-25%, AND could accidentally reopen the majority-vote shortcut on
whichever families end up in test. Fixed with an exact (deterministic,
no randomness) search over all same-size family combinations, picking the
one that both lands the ratio in-band and minimizes the majority-vote
shortcut on the resulting test set.
