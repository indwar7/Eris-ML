# build_raw.py

Fetches the raw material for the "Digitization Pipeline Attribution"
challenge: real historical-newspaper OCR text (Chronicling America / NDNP,
Library of Congress), grouped by the real digitization batch it came from.

Run: `python build_raw.py [out_dir]` (defaults to `dataset/raw/`). Safe to
re-run -- it resumes from whatever batches are already in
`dataset/raw/batches_meta.csv` rather than re-fetching them.

## Not byte-identical reproducible

This is a **live fetch from a public archive**, not a deterministic
generator over a fixed corpus. Re-running it later will not necessarily
reproduce exactly the same set of batches or snippets: the mirror's batch
index can change (batches added/withdrawn/renamed -- several candidate
batch_ids that exist in the index 404'd on the actual fetch), page-level
fetches are subject to intermittent timeouts and rate limiting, and the
evenly-spaced issue-date sampling depends on exactly which issues are listed
in a batch's manifest at fetch time.

This is the same convention used by this project's other real-data
challenges (e.g. `cpu/recompile`, `cpu/palimpsest`): the **committed
`dataset/raw/` files are the frozen source of truth** for the challenge going
forward. `build_raw.py` documents and can replicate the fetch approach, but
it is not meant to be re-run to regenerate the exact same corpus.

## What it does

For each candidate `batch_id` (a real NDNP award, one institution digitizing
one or more newspaper titles through one contracted OCR vendor pipeline):

1. Fetch `batch.xml` -- the batch's own manifest of every issue it contains.
2. Evenly sample up to 18 distinct issue dates spread across the batch's run.
3. For each sampled issue, fetch its (small) METS file to find the ALTO OCR
   file for its first page, then fetch that page.
4. Keep every `<TextBlock>` with at least 40 characters of OCR text (capped
   at 14 per page) as one snippet, along with the real
   `softwareCreator` / `softwareName` / `processingAgency` fields recorded in
   that page's own `<OCRProcessing>` metadata.

A batch is skipped if its manifest lists fewer than 4 distinct issue dates,
or if it yields fewer than 60 snippets after fetching.

## Known gotchas (see `dataset/raw/meta.json` for what actually happened)

- Skipped candidates are persisted in `meta.json` under `skipped_batches`
  (`{batch_id: reason}`), merged and rewritten at the end of each run, so
  re-runs do not re-attempt known-404 batch IDs. A run that dies mid-way
  loses only that run's new skips (a few cheap 404 re-fetches next time).
- The modern `chroniclingamerica.loc.gov` API and `loc.gov` endpoints sit
  behind Cloudflare and 403 for programmatic access; only the plain
  static-file mirror at `chroniclingamerica.loc.gov/data/batches/` works.
- The mirror rate-limits aggressive crawling (HTTP 429). The fetcher paces
  requests (~1.1s apart) and backs off 30s on a 429 rather than hammering
  through it.
- Different batches' `batch.xml` files were generated by different NDNP
  tooling versions and disagree on XML attribute order -- parse with
  namespace-stripped ElementTree, not a fixed-order regex.
